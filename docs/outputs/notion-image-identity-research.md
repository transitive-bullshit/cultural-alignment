# Notion image identity and download short-circuiting

Research date: 2026-08-31

## Implemented decision

The implementation keeps immutable, content-addressed WebP variants in the public media bucket and moves reusable media state to one stable JSON descriptor per Notion record:

```text
media/state/{collection}/{compact-notion-page-id}.json
```

Descriptors use `S3_STATE_BUCKET_NAME` when set and otherwise default to the media `S3_BUCKET_NAME`. Normal reuse performs one authenticated `GET` and validates the JSON body. It does not issue a descriptor `HEAD`, duplicate state into custom metadata, or implement the minute-rounded settling protocol explored in the original recommendation. This section supersedes those earlier alternatives. A separate state bucket remains available when storage-level isolation is useful, but it is not required.

When the descriptor's page marker and media-pipeline version match, sync skips block traversal, source download, and Sharp. Optional sources without posters store an `absent` state and skip repeat empty-page scans too. When the page marker changed, sync scans the current selection and compares the selected block ID plus block `last_edited_time`; external and configured fallback identities also include their URL. A matching source keeps the existing variants and refreshes the descriptor's presentation facts. A miss, source change, pipeline change, or `--force` downloads and processes the image.

Variants are still hashed before publication and written first. The descriptor is conditionally created with `If-None-Match: *` or replaced with `If-Match` against the ETag returned by `GET`. Force bypasses reuse and always reruns download and Sharp, but an identical generated hash may reuse an existing immutable variant.

## Pre-migration repository behavior

Before the descriptor migration, the fast path in `reusableImageEntry` required a manifest entry whose `lastEditedTime` exactly matched the Notion page's `last_edited_time`. It reconstructed the content-hash gallery and detail keys, performed two destination existence checks, and returned the saved media result. An unchanged page therefore incurred:

- the page row read that the content sync already performs;
- two R2 `HeadObject` calls; and
- no image-block traversal, Notion image download, or Sharp processing.

The only legacy exception is an old reusable entry missing `blurDataURL`, for which the code downloads the already-generated gallery variant to recreate the blur placeholder. Current schema-version-2 entries include the blur value.

That shortcut had a separate correctness assumption: Notion documents timestamps on pages and blocks, but does not document that editing every nested or synced child will advance the containing page's timestamp. The implemented design deliberately retains the page marker as its simple clean-record fast path and scans block identity only after a page-level change.

When the page timestamp differed, the old flow traversed the page's blocks, selected the image, downloaded it, computed `sourceHash = SHA-256(input)`, ran Sharp for gallery/detail variants and the blur placeholder, then hashed the generated variants. Thus a page-only edit caused expensive Notion/Sharp work, although identical generated bytes were not uploaded again.

## Evidence from repository history

I compared every adjacent checked-in `content/snapshot/manifest.json` after commit `21aa9d4` (“move image assets to S3/R2”), joining scenario and source media entries by Notion page ID. For common entries whose `lastEditedTime` changed, I compared `sourceHash`:

| Manifest transition | Page-timestamp invalidations | Same `sourceHash` | Changed `sourceHash` |
| --- | --: | --: | --: |
| `21aa9d4` → `aff46a6` | 0 | 0 | 0 |
| `aff46a6` → `00846a5` | 537 | 536 | 1 |
| `00846a5` → `01bdef4` | 5 | 5 | 0 |
| `01bdef4` → `e83dbb4` | 0 | 0 | 0 |
| `e83dbb4` → `9a6b211` | 47 | 45 | 2 |
| **Total** | **589** | **586** | **3** |

Because `sourceHash` is computed directly from the downloaded input bytes, 586 of 589 observed page-timestamp invalidations—**99.5%**—reprocessed byte-identical source images. Three transitions contained genuine source-byte changes.

This is repository-history evidence, not an event log. It sees only committed manifest transitions; multiple runs or edits between commits are collapsed; the same record can count in multiple transitions; and newly added or removed records are excluded. “Changed bytes” means the downloaded representation's SHA-256 changed, not necessarily that a person intentionally replaced the image.

The pre-migration v2 manifest contained 613 scenario/source media entries. All 613 page timestamps matched `:00.000Z`, across only 70 distinct timestamp values. That local observation agrees with Notion's documented minute rounding and motivated the settling-guard investigation; the implemented KISS design knowingly accepts the practical invalidation limitation and provides `--force` for explicit full verification.

## Options and trade-offs

| Approach | Steady-state source work | Correctness / operational trade-off | Verdict |
| --- | --- | --- | --- |
| Old page-manifest fast path | Two R2 `HEAD`s; no image read when the page marker matches | Fast for unchanged pages, but any page edit triggered block traversal/download/Sharp; 586/589 observed invalidations had identical source bytes | Superseded |
| Add block marker to existing manifest | Resolve selection, then compare `(block ID, block edit time)`; page marker can be a hint | Smallest code change, but media state remains checked into Git and grows with the corpus | Not selected |
| Put Notion “revision” in variant keys | `HEAD` a directly derived key | No real revision exists; rounded timestamps collide, metadata edits create duplicate generations, and direct revision keys lose content-addressed reuse | Reject |
| Stable R2 descriptor + immutable variants | One small authenticated JSON `GET`; no source image read on reuse | R2 becomes media-state authority, retains content-hash variants, and supports descriptor-last conditional publication; adds one small object per record, with an optional separate state bucket | **Implemented** |
| Signed URL identity / conditional source `GET` | Fresh Notion URL plus a source request per candidate | Full URL always churns; unsigned path is unsupported; conditional GET currently works but Notion does not contractually expose its ETag and source `HEAD` returned 403 | Optional validation fallback |

## Implemented R2 descriptor protocol

### Object layout and fields

Use one stable key per record, not per selected block:

```text
media/state/{collection}/{compact-notion-page-id}.json
```

Per-record scope matters because the result also depends on page-owned selection rules, image order/override, fallback choice, caption, and additional-image count. The current code recursively enumerates full image blocks in depth-first order, uses the configured scenario override when present and otherwise the first image, then uses a configured/video fallback only when no image is selected.

The descriptor lives in `S3_STATE_BUCKET_NAME` when configured; otherwise that setting defaults to `S3_BUCKET_NAME`, placing state and variants in the same bucket. Descriptor responses use `Cache-Control: private, no-store`; generated variants use a year-long immutable cache policy. The descriptor cache directive is not access control: if the shared bucket has an unauthenticated delivery origin, `media/state/` keys may also be publicly addressable unless that delivery layer restricts the prefix. A distinct, non-public state bucket remains an optional deployment choice.

The descriptor JSON body contains the complete reusable state:

```text
schemaVersion
collection
notionId
pageLastEditedTime
pipelineVersion
state: image | absent
source:
  Notion file: { blockId, blockLastEditedTime }
  Notion external: { blockId, blockLastEditedTime, url }
  configured fallback: { imageBlockId, url }
media (image state only): {
  sourceHash, galleryHash, detailHash,
  galleryKey, detailKey,
  width, height, blurDataURL,
  additionalImageCount, caption
}
```

For an external or configured fallback source, the exact stable URL/config identity participates in comparison. A temporary signed Notion-hosted URL does not. `additionalImageCount` and caption are presentation facts: after a changed-page scan they can update without forcing image processing when source identity is unchanged.

### Read flow

1. Authenticated `GET` the record's descriptor from the configured state bucket and strictly validate its JSON body and record binding.
2. Unless forced, reuse immediately when descriptor pipeline and page `last_edited_time` match. No block traversal, source request, Sharp work, or variant existence request is made.
3. Otherwise, resolve the current image selection without fetching its bytes. If the descriptor pipeline and structured source identity match, reuse the variants and conditionally refresh the page marker, caption, and additional-image count.
4. If the descriptor is missing, a checked-in v2 media entry may seed it after current selection and legacy variant validation.
5. On a miss, changed source, pipeline change, or force, download and process the source.

### Variants first, descriptor last

1. Download and process only when the read flow requires it.
2. Hash each generated variant and publish it at the existing immutable content-hash key with `If-None-Match: *`; concurrent writers producing identical bytes converge safely.
3. Wait for all referenced variants to succeed.
4. Write the stable JSON descriptor last: use `If-None-Match: *` when absent or `If-Match: <ETag returned by GET>` when replacing it. A stale concurrent writer fails instead of blind-overwriting newer state.

AWS documents `If-None-Match` as create-only and `If-Match` as an ETag comparison that rejects a stale writer; it also documents `412` and possible concurrent `409` outcomes ([S3 conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)). R2 exposes those conditional `PutObject` operations and provides strong global read-after-write and metadata consistency ([R2 S3 compatibility](https://developers.cloudflare.com/r2/api/s3/api/), [R2 consistency model](https://developers.cloudflare.com/r2/reference/consistency/)).

Publishing the pointer last means a crash can leave only unreferenced immutable variants; it cannot publish a descriptor that points at an object this run has not successfully created. Do not eagerly delete superseded variants. A later descriptor-based mark-and-sweep or retention policy can collect orphans independently.

## Chosen KISS boundary

The investigation identified that Notion edit times are minute-rounded and are not exact byte revisions. The implementation intentionally does not add provisional generations, clock margins, later-run settling, or source-ETag validation. It treats page and block edit markers as practical invalidation hints. `--force` is the explicit escape hatch when an operator wants to disregard those hints and verify every source through a full re-download and reprocess.

## Implemented `--force` contract

`--force` is unambiguous and complete:

1. Bypass page-timestamp, descriptor-source, and pipeline reuse decisions for every media record.
2. Perform an unconditional source `GET`, rerun Sharp for gallery, detail, and blur output, and recompute source/output hashes and dimensions.
3. Preserve content-addressed semantics: if reprocessing produces an already-existing immutable variant key, destination deduplication may reuse that object. Force means “re-download and reprocess,” not “store duplicate identical bytes.”
4. Publish variants first, then conditionally refresh the descriptor using the ETag read at the start. Never blind-overwrite a concurrent descriptor and never delete prior variants as a side effect.

Because the descriptor is committed last, a failed force run leaves the previous valid descriptor readable.

## Boundary with the checked-in manifest

Moving media reuse state to R2 does **not** delete `content/snapshot/manifest.json`. After the first authenticated migration, manifest schema v3 owns stable slug allocation for scenarios, sources, risk families, and concepts, plus snapshot counts, fixture IDs, Notion source contracts, and output validation ([manifest schema](../../scripts/sync-manifest.ts)).

Only the scenario/source media entries—the image provenance, hashes, variant pointers, dimensions, caption, and blur placeholder—move to per-record R2 descriptors. The generated snapshot still contains the public presentation fields it needs. During the first v2-to-v3 run, a missing descriptor can be seeded from a matching, validated legacy media entry; descriptors are written before the staged v3 manifest can commit, so a failed migration remains retryable from v2.

## What the read API actually exposes

### Image block identity

Every block has a UUID `id` and `last_edited_time`; Notion defines the latter as the date and time when the block was last updated. The documented block fields do not include a version or revision number. Image blocks add a file object plus caption, not another image-specific identifier ([Block object](https://developers.notion.com/reference/block)).

Block IDs are the strongest supported identity value. Notion's versioning policy says record identifiers such as page and block IDs are guaranteed stable UUIDs, while opaque values not documented as stable may change in structure and must not be parsed ([Versioning policy](https://developers.notion.com/reference/versioning)).

An editor can change the file attached to an existing media block through the Update Block API, so a block ID by itself does not identify its image bytes. Notion's file-upload guide explicitly lists changing the file attached to an existing block as a supported update ([Uploading small files](https://developers.notion.com/guides/data-apis/uploading-small-files)). Conversely, deleting the old block and inserting a new image produces a different block record and therefore a different block ID.

### `last_edited_time` is not a revision number

`last_edited_time` is the closest documented change signal, but it has two important limitations:

- It describes the whole block. A caption-only or other metadata edit can advance it even though the source bytes did not change, causing a conservative cache miss.
- Notion announced that `last_edited_time` and `created_time` for page, database, and block objects are rounded down to the closest minute ([historical changelog, June 28, 2021](https://developers.notion.com/guides/resources/historical-changelog)). Current API responses still exhibit minute-shaped values, and a live project image retrieved during this research returned a timestamp ending in `:00.000Z`.

That rounding creates a real false-negative case for an unguarded cache: process an image near the start of minute M, replace the file later in minute M while retaining the block, and both observations can expose the same `(block id, last_edited_time)`.

The research considered a provisional-generation settling rule to narrow that gap, but it was not selected. The implemented design keeps the markers simple and exposes `--force` for an operator-requested byte-level refresh.

This is still an invalidation scheme, not mathematical proof of byte identity. Notion does not promise that its backing-store representation can never change without a block edit.

### Page-level edit time

Pages also expose `last_edited_time`, defined as the time the page was updated ([Page object](https://developers.notion.com/reference/page)). Notion recommends filtering queried rows by `last_edited_time` or using integration webhooks for incremental sync of large data sources ([April 20, 2026 changelog](https://developers.notion.com/page/changelog)).

That value is useful as a coarse page-selection optimization, but it is not image identity:

- it is rounded to the minute as well;
- any unrelated page edit can invalidate the page generation;
- it cannot distinguish which image block changed;
- it is the only comparable parent-level signal for covers, icons, and file properties, which lack an image-block ID.

For image blocks, block-level provenance is more selective after the page has been traversed. If page timestamps are used to avoid querying unchanged pages, the cursor/window needs overlap for minute rounding rather than a strict exclusive cutoff.

## File-source variants

Notion's file object has three source types ([File object](https://developers.notion.com/reference/file-object)):

| Read/write form | Stable value exposed on read? | Suitability as content identity |
| --- | --- | --- |
| `file` (Notion-hosted) | Temporary `url` and `expiry_time` only | No exact identity marker |
| `file_upload` (API upload handle) | UUID while creating/attaching the upload | Potentially useful only if the writing integration retained it separately; it is not returned from the attached block |
| `external` | Original URL, returned as-is and non-expiring | Stable location descriptor, not proof of immutable bytes |

### Hosted `file`

Notion says each fetch of a hosted file includes a temporary public URL valid for one hour, explicitly advises clients not to cache or statically reference it, and requires refetching the file object to refresh access ([File object](https://developers.notion.com/reference/file-object), [Retrieving existing files](https://developers.notion.com/guides/data-apis/retrieving-files)). Its schema exposes only:

- `url`
- `expiry_time`

There is no checksum, content length, original upload ID, file creation time, or ETag in this read shape.

Hashing the full signed URL cannot work as an unchanged-file test because its signature and expiry inputs change. Stripping the query string currently produces a path that often appears stable, but that path is not documented as an identifier. Notion guarantees record IDs, not storage URL hosts or path components, so parsing the URL would be an unsupported heuristic.

### `file_upload`

The File Upload API creates a UUID handle and exposes useful lifecycle metadata: creation and edit times, status, filename, MIME type, and content length. It still exposes no checksum ([File Upload object](https://developers.notion.com/reference/file-upload)). More importantly, after a File Upload is attached to a media block, the read response becomes type `file`, not `file_upload`, so the block returns a download URL rather than the File Upload ID ([Block file fields](https://developers.notion.com/reference/block), [Retrieving existing files](https://developers.notion.com/guides/data-apis/retrieving-files)). Page icons similarly document `file_upload` as write-only and `file` as read-only ([Page properties](https://developers.notion.com/reference/page-property-values)).

Consequences:

- UI-uploaded images never expose a File Upload ID.
- API-uploaded images do not round-trip that ID through normal block/page reads.
- An integration that created an upload could retain its ID itself, but that reintroduces side state and does not help existing workspace images.
- Listing uploads only recovers uploads belonging to the current bot connection and does not provide an attached-block-to-upload mapping ([List file uploads](https://developers.notion.com/reference/list-file-uploads)).

### `external`

Notion promises to return an external file URL as-is and says those links never expire ([File object](https://developers.notion.com/reference/file-object)). Hashing the URL therefore detects a URL replacement without involving the hosted file's bytes. It cannot detect an origin replacing the bytes at the same URL. Strict sync for external images needs one of:

- an application-level rule that external asset URLs are immutable;
- origin-supplied HTTP validators through a conditional request;
- or a normal download and content hash.

This applies equally to fallback URLs such as mutable thumbnail endpoints: a Notion block timestamp cannot describe changes at that external origin.

## Signed URL and HTTP-validator observations

Notion documents hosted URLs as authenticated HTTP **GET** URLs, not as general S3 credentials ([File object](https://developers.notion.com/reference/file-object)). On 2026-08-31, a read-only probe against one current project image observed:

| Probe | Result |
| --- | --- |
| Fetch image block twice | Full URLs differed |
| Compare the two URLs | Origin and path matched; signed query strings differed |
| `HEAD` signed URL | `403` |
| `GET` with `Range: bytes=0-0` | `206` and an `ETag` header |
| Fresh `GET` with `If-None-Match: <prior ETag>` | `304` |

This is useful current behavior, not a Notion guarantee. It confirms three points:

1. Source `HEAD` cannot be assumed to work with a GET-signed URL.
2. A conditional `GET` can presently avoid transferring and reprocessing unchanged bytes.
3. The apparently stable unsigned path should still not be promoted to a contract.

Amazon S3 defines an ETag as identifying a specific object content version, while warning that it is not necessarily an MD5 digest for encrypted or multipart objects ([S3 object integrity](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html)). Treating an ETag as an opaque HTTP validator is therefore appropriate; treating it as Notion's documented file hash is not.

An optional validator path could store the last observed source ETag, obtain a fresh Notion URL, issue `GET` with `If-None-Match`, reuse on `304`, process the `200` body, and fall back to a normal GET whenever the origin omits or rejects the validator. It still costs a source request for each candidate and is not part of the implemented KISS path.

## Candidate markers and verdicts

| Candidate | Catches a Notion image replacement? | Safe short-circuit by itself? | Verdict |
| --- | --- | --- | --- |
| Block ID | Only if replacement creates a new block | No; an existing block's file can be updated | Include in provenance |
| Block ID + block `last_edited_time` | Normally; same-block edits advance the edit time | Not absolutely; timestamps are minute-rounded | Implemented pragmatic hint; `--force` is the escape hatch |
| Page ID + page `last_edited_time` | Normally, at page granularity | Not exact and over-invalidates | Coarse prefilter only |
| Full hosted signed URL | Yes, but also changes on credential refresh | No; near-permanent misses | Do not use |
| Hosted URL without query string | Appears to in current behavior | No documented stability or semantics | Do not rely on as truth |
| `expiry_time` | No | No | Access lifecycle only |
| File Upload ID | Yes when retained by the uploader | Not available on attached-file reads | Inapplicable to the general sync |
| External URL | Detects URL changes | No if origin bytes are mutable | Use only with an immutability policy |
| Source HTTP ETag | Detects representation changes when the host honors it | Not exposed or guaranteed by Notion | Optional conditional-GET validator |
| Webhook event ID/timestamp | Signals that an event occurred | No; event does not contain file identity or content | Incremental scheduling aid only |

Notion's `page.content_updated` webhook can include updated block IDs, but webhook events are signals that require a follow-up API retrieval and do not carry the changed content ([Webhook events and delivery](https://developers.notion.com/reference/webhooks-events-delivery)). They can reduce polling in an always-on integration, but they do not solve destination-only media identity.

## Direction applied to this repository

After the first authenticated migration, R2 is the media-state authority without a separate checked-in media index: one authenticated descriptor `GET` provides the complete reusable state. Clean page and pipeline markers short-circuit all deeper media work; changed pages scan the selected block identity before deciding whether to download. Immutable content-hash variants remain the public delivery facts, and the descriptor is their conditionally written mutable pointer. This gets the intended common case—a small authenticated JSON read and no Notion image transfer—without a descriptor `HEAD`, custom metadata encoding, or settling state machine.

## API-version assessment

The latest Notion API version on the research date is `2026-03-11`. Its breaking changes concern block insertion position, `archived` versus `in_trash`, and the `transcription` to `meeting_notes` rename; none add or remove media identity fields ([Changes by version](https://developers.notion.com/reference/changes-by-version)). The previous current line, `2025-09-03`, reorganized databases into databases and data sources, also without changing image identity.

Notion's versioning policy says additive features do not require a new API version, so File Upload API availability is not evidence that a newer `Notion-Version` will expose upload IDs on reads ([Versioning policy](https://developers.notion.com/reference/versioning)). As of `2026-03-11`, no supported version exposes a hosted-file checksum, ETag, media revision, or retained File Upload ID through an attached image block.
